# Local two-instance prototype protocol

The server listens only on 127.0.0.1:9001. Each connection authenticates with `{"type":"auth","token":"demo-alice"}` or `demo-bob`; the server maps these fixed demonstration tokens to `alice` and `bob`. These public constants are not production credentials and are unsuitable for untrusted users. User identity is associated with the connection; a caller-supplied user ID is never trusted.

After `auth_ok`, send `{"type":"join","room_id":"room_001"}` to join, `{"type":"leave","room_id":"room_001"}` to leave, or `{"type":"send","room_id":"room_001","client_msg_id":"1","content":"hello"}` to send. A sender must be in the room. Every connection currently subscribed to that room, including the sender, receives a `message` event. `ping` can be sent before login and returns `pong`. Errors have `type: error` and a `message` field.

Each accepted send is persisted before a local broadcast. The sender first receives `send_ok` with the server-assigned `message_id` and `duplicate` flag. `(sender_id, client_msg_id)` is unique; an identical retry returns the same ID without rebroadcast, while different room or content with the same key is rejected. A `message` event carries the ID, sender, room, client ID, content and UTC `created_at` timestamp. SQLite uses WAL, a busy timeout, indexed history and transactions; it still allows only one writer at a time.

After joining, `{"type":"history","room_id":"room_001","after_message_id":0}` returns up to 100 messages in ID order. Omit `after_message_id` to query after the user's stored ACK cursor. `{"type":"ack","room_id":"room_001","message_id":1}` advances that cursor monotonically when the message exists in that room. A cursor confirms a prefix, so clients must only ACK a message once they have processed all earlier messages they need. Repeated pulls can return the same message; clients should deduplicate using `message_id`.

Database work is run by a dedicated thread with one SQLite connection and at most 256 outstanding operations; completion is deferred to the event-loop thread and resolves the connection by ID. If full, the request receives an error and can be retried. A successful `send_ok` denotes a committed database write, not guaranteed delivery to every client. Room names and tokens are capped at 64 bytes, client IDs at 128 bytes, content at 4096 bytes, rooms per connection at 32, and incoming frames at 16 KiB. Idle timeout is 30 seconds, automatic pings are enabled and the configured per-connection backpressure limit is 64 KiB with closure on limit. No load or timeout behavior has been measured yet.

For a newly stored message, the originating instance broadcasts locally and enqueues a Redis event containing its instance ID and message. The subscriber ignores events from its own instance and sends other events to local room subscribers through `Loop::defer`. Publisher and subscriber own separate Hiredis connections and threads. Subscriber reconnects and subscribes again after a failure. Publish and deferred-delivery queues are bounded to 256; overflow or Redis failure is logged and may lose live delivery. Neither SQLite and Redis nor a Pub/Sub event and client delivery form an atomic transaction. After failure, query SQLite history; Redis Pub/Sub itself retains no offline messages. Identical send retries do not rebroadcast. This is not end-to-end exactly-once.

`python3 tests/phase2.py` tests the single-instance path. `python3 tests/phase4.py` starts two independent processes and an isolated Redis, verifies cross-instance delivery, stops and restarts Redis, and checks client offline history recovery. The tests only demonstrate a single host and the exercised failure paths.
