# 简历描述与面试问题（以本地实测范围为准）

## 简历项目描述

基于 C++17、uWebSockets、Redis Pub/Sub 和 SQLiteCpp 实现单机双进程实时消息演示服务。支持演示令牌认证、房间订阅与消息广播；使用独立 SQLite 工作线程持久化消息，基于发送者与客户端消息 ID 去重，提供 ACK 游标和历史补拉。通过独立 Redis 发布/订阅线程实现跨实例转发与订阅重连，使用 `Loop::defer` 将后台结果交回连接所属事件循环。使用 CMake、GoogleTest 和 Python 客户端完成双实例通信、Redis 中断恢复、重启补拉和异常输入测试。该系统是本机演示，不宣称生产级高可用或端到端 exactly-once。

## 结合代码的问题

1. **为什么不能从 Redis 线程直接调用 WebSocket？** 连接属于 uWebSockets 事件循环；`main.cpp` 用 `Loop::defer` 把任务交回该线程。
2. **后台任务完成时连接已断开怎么办？** 用连接编号查询当前表，找不到就不向该连接回复，避免保存悬空 socket 指针。
3. **为什么 SQLite 和 WebSocket 不共用事件线程？** SQLite 写入与锁等待可能阻塞，`StorageWorker` 负责专用连接和有界任务队列。
4. **消息写入的去重键是什么？** `messages` 表约束 `(sender_id, client_msg_id)`；相同内容的重试返回原 ID，冲突内容报错。
5. **为什么先保存再发布？** 服务端只在提交成功后生成广播；发布失败仍可以从数据库查询，不等于原子跨系统提交。
6. **如何避免本地广播后收到自己的 Redis 回传？** 事件带实例 ID，订阅端过滤自己的 ID；不同进程必须配置不同 ID。
7. **Redis 中断后的行为是什么？** 实时事件可能丢失，订阅线程会重新连接并订阅，缺失消息通过 SQLite 历史查询。
8. **是否实现 exactly-once？** 没有。消息行可去重，但推送可能丢失或重复，客户端应以 message_id 去重并补拉。
9. **ACK 游标有何语义？** 系统逐条记录 ACK，只在较早消息都已确认时推进房间前缀游标；缺口后已确认的消息在补拉时仍可能重复出现。
10. **为何采用 WAL 和 busy timeout？** WAL 改善读写并发，busy timeout 允许短暂锁竞争等待；SQLite 仍只允许一个写事务。
11. **如何防止后台队列无限增长？** SQLite 待完成操作和 Redis 发送/投递队列设置上限；满时返回错误或记录丢失并依赖补拉。
12. **如何限制慢连接？** uWebSockets 配置 `maxBackpressure` 及超限关闭；这是框架提供的能力，不应称为自研网络栈。
13. **如何处理超长或非法输入？** 限制帧及字段大小、校验 JSON 和字段类型；自动化测试覆盖非法 JSON 与超长帧。
14. **认证是否适合生产？** 不适合，固定演示 token 仅用于本机；没有 TLS、密码管理和真实用户授权体系。
15. **如何验证跨实例及故障恢复？** `tests/phase4.py` 启动两个真实进程和临时 Redis，停启 Redis 并验证订阅恢复与补拉。
16. **基准结果能代表生产容量吗？** 不能。`docs/performance.md` 明确记录 8 客户端、5 秒、tmpfs 和 ACK 延迟的范围。
17. **两个实例为何可能争用数据库？** SQLite 同时只允许一个写事务；初始化和写入遇到 busy/locked 时做有限重试，仍可能超时，不能保证高并发。
18. **正常退出时发生什么？** 信号由专门线程等待，通过事件循环关闭 socket，线程析构时回收连接；尚未发送的实时事件应通过历史恢复。
