# 阿里云服务器部署与验证记录（2026-11-24）

- 实例：Ubuntu 24.04.5 LTS、x86-64、2 vCPU、约 3.5 GiB 可用总内存、ext4 系统盘。
- 源码目录：`/opt/CppRealtimeMessagingServer`；数据与日志目录：`/opt/CppRealtimeMessagingServer-data`。
- 安装系统包：`redis-server` 7.0.15 和 `pkg-config`，含其包管理器依赖。Redis systemd 服务启用，实测仅监听 `127.0.0.1:6379` 和 `[::1]:6379`。
- C++：GCC 13.3.0、CMake 3.28.3、SQLite 3.45.1，Hiredis 1.6.0 从固定源码构建。`cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug` 和 `cmake --build build -j2` 成功。
- `ctest --test-dir build --output-on-failure`：12/12 通过，用时 46.87 秒。包含 Redis 断连重订阅、离线补拉、SQLite 锁错误、非法输入、心跳和慢客户端背压测试。测试使用自己的临时进程和端口。
- 部署的两个真实进程分别监听 `127.0.0.1:9001`、`127.0.0.1:9002`；Redis 频道有两个订阅者。`python3 scripts/check-demo.py` 验证持久化、跨实例投递和 ACK，测试写入独立房间。
- 两个消息服务通过脚本在后台启动，没有配置为服务器开机自启服务；Redis 软件包已启用 systemd 服务。实例重启后需要按部署说明恢复消息服务。

## 短时并发测试

8 客户端、每客户端不主动限速、16 字节内容的 5 秒压测有一次 SQLite 写锁超时；服务向客户端返回 `storage failure`。这次测试未得到有效吞吐量，不将其计作通过。SQLite 只允许一个写事务，该测试不足以单独确定具体锁竞争原因或生产容量。

随后使用 `python3 tests/cloud_benchmark.py`，两客户端分别连接两个临时实例、各自独立房间，每次确认后等待 50 毫秒再发送，内容为 16 字节；Redis、SQLite 和服务均为本机隔离测试实例，数据库位于服务器 `/tmp`（ext4）。实际持续 5.007 秒，成功 188 条、错误 0 条，37.55 条/秒；客户端等待服务端 `send_ok` 的 p50/p95/p99 分别为 2.993/3.362/3.515 毫秒。该速率由客户端刻意限速，不是服务器最大吞吐能力，亦不是跨实例端到端消息延迟。

当前项目只用于单机双实例演示：公开演示令牌、无 TLS、SQLite/Redis 非原子提交和 Redis Pub/Sub 非持久化不适合直接暴露公网或宣称生产级高可用。不要开放 Redis 公网端口。

## 恢复与写锁修复的隔离验证

在服务器独立测试目录，Redis 静默重启后首条消息可再次跨实例送达；重复 Redis 事件被近期事件缓存抑制。ACK 改为记录单条消息并仅推进连续前缀；旧版游标在迁移时保留备份、重置为零以避免遗漏历史，可能重放已读消息。基于线上 SQLite 的临时副本完成迁移试跑：消息数 2、旧游标数 2，`PRAGMA integrity_check` 返回 `ok`。

加入 SQLite 锁的有限退避重试后，隔离目录 14/14 项测试通过；包括短暂锁释放后重试成功、持续锁定最终报错、乱序 ACK 和静默重启。相同服务器再次进行 8 客户端、16 字节内容、每次收到本地事件后立即发送下一条的 5 秒压力测试：实际 5.093 秒、成功 1632 条、错误 0、320.46 条/秒，ACK p50/p95/p99 为 12.006/13.571/544.767 毫秒，临时数据库位于服务器 `/tmp`（ext4）。该脚本的 JSON 输出中的 `WSL /tmp` 标签是硬编码，实际测试运行在云服务器，不是 WSL。单次结果不能证明高并发无故障或确定生产容量。
