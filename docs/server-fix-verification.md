# 服务器消息恢复修复及验证记录（2026-11-24）

## 已部署内容

- Redis 发布的 TCP 连接失效时，会重新连接并对当前事件最多重试一次；接收端通过有界近期事件缓存抑制可能的重复推送。
- ACK 逐条记录，只有连续已确认消息才能推进房间游标。历史查询可能重放缺口之后已经确认的消息，客户端仍需按 `message_id` 去重。
- SQLite 写入和 ACK 遇到 BUSY/LOCKED 时进行有限退避重试；持续争用仍可能返回 `storage failure`，SQLite 仍只有一个写事务。

升级前使用 SQLite backup API 创建数据库一致性备份，并备份旧程序和受影响源码，位于：

```text
/opt/CppRealtimeMessagingServer-data/backups/before-reliability-20261124T064309082703Z/
```

旧游标无法证明之前没有漏消息，因此迁移事务将其复制到 `user_room_offsets_legacy` 后重置当前游标，以保守重放历史。用户可能重新收到已读消息。线上只读比对结果：升级前 2 条消息均保留、2 条旧游标均保留，迁移标记存在，`PRAGMA integrity_check` 为 `ok`。更新后两实例消息与 ACK 实测通过。

## 实测

- 服务器 Ubuntu 24.04、2 vCPU、ext4。部署目录 `ctest --test-dir build --output-on-failure`：**14/14 通过，53.19 秒**，覆盖 Redis 静默重启后的首条消息、重复事件、乱序 ACK、旧库迁移、SQLite 锁重试与最终失败、心跳及背压。
- 本次隔离压测：8 客户端、16 字节内容、计划 5 秒、实际 5.093 秒，1632 条成功、0 错误，320.46 条/秒；ACK p50/p95/p99：12.006/13.571/544.767 毫秒。数据库在服务器 `/tmp`，文件系统 ext4；该单次短测不代表容量保证。此前同配置的旧版出现过 SQLite 写锁超时。
- Redis 重试遇到响应丢失时，首次发布是否成功不可判定；缓存最多保存 8192 个近期事件键，进程重启或缓存淘汰后仍可能重复。数据库和 Redis 不具备原子提交；极端情况下仍需历史补拉，不能声称 exactly-once。

两个服务只监听服务器回环地址。它们是后台进程，未配置服务器重启后自动启动；Redis 为系统服务。
